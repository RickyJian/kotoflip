# DECISION

## 新增單字卡 UI/UX 流程

**討論**：新增單字卡的操作情境與畫面流程。
**決定**：
- Home 頁點擊「新增」按鈕 → 導向獨立的新增單字卡 Page。
- Page 中央顯示一張正方形卡片，可正反翻面：
  - 正面：左上角以淡色文字顯示 placeholder「原文」
  - 背面：左上角以淡色文字顯示 placeholder「譯文」
- 卡片下方（卡片範圍外）顯示 label 新增區塊，label 最多 10 組。
- 點擊「完成」→ 新增成功（存檔）。
- **流程 1（編輯剛新增的卡片）**：卡片右上角顯示編輯 icon，點擊後將 readonly 欄位切換為 edit mode。
- **流程 2（連續新增）**：點擊「新增」按鈕 → 前一張卡片 swipe 至左側、疊在新卡片下方，後續操作同上。
- **限制**：尚未存檔的卡片不可 swipe 到其他卡片；只有 read mode 才允許 swipe（edit mode 下鎖定 swipe）。
**理由**：讓使用者能連續、快速地新增多張單字卡，並保留即時編輯剛新增內容的彈性，同時避免未存檔資料因 swipe 手勢而遺失或混淆。
**時間**：2026-07-11

## 翻面手勢與範圍界定

**討論**：卡片翻面的觸發方式，以及「編輯剛新增卡片」（流程 1）是否納入本次規劃範圍。
**決定**：
- 正面（原文）輸入完成按送出 → 自動翻到背面（譯文）；背面輸入完成後停留在背面，不自動翻回正面。
- 流程 1（編輯功能）**不列入本次 plan 的實作範圍**，僅作為未來規格保留紀錄；編輯時需先翻到對應面才能編輯該面欄位。
**理由**：先聚焦「新增」流程本身，編輯功能留待後續獨立規劃（對應 SPECS.md 的「編輯單字卡」）。
**時間**：2026-07-11

## 完成後導向

**討論**：全部新增完成後如何離開新增 Page。
**決定**：點擊「完成」→ 導回 Home。
**理由**：與單張卡「完成」語意一致，且不需要額外的頁面內離開按鈕。
**時間**：2026-07-11

## 儲存方式

**討論**：本地儲存機制選型。
**決定**：採用 sqlite。
**理由**：結構化資料（單字卡 + label 關聯）較適合關聯式查詢，且第一階段之後有統計資訊、進階 shuffle 等需求，sqlite 較好擴充查詢條件。
**時間**：2026-07-11

## 欄位驗證規則

**討論**：原文、譯文、label 的必填與長度限制。
**決定**：
- 原文：必填，100 字元內
- 譯文：必填，100 字元內
- label：必填，20 字元內
  - 第一張卡片：label 預設為「預設群組」
  - 第二張卡片起：預設帶入「上一張卡片的 label」
**理由**：避免無意義的空白單字卡；label 預設延續上一張，減少連續新增時的重複輸入。
**時間**：2026-07-11

## label 輸入方式

**討論**：label 新增區塊的輸入方式。
**決定**：手動輸入為主，支援 autocomplete，從曾經輸入過的 label 歷史紀錄中自動帶出建議。
**理由**：兼顧靈活分類與輸入效率，避免同義但打字不同的 label 造成分類破碎。
**時間**：2026-07-11

## 疊卡視覺張數上限

**討論**：連續新增時，畫面上堆疊卡片的視覺呈現張數上限。
**決定**：視覺堆疊最多顯示 3 張（最上層為編輯中卡片，往下疊 2 張）；超過的卡片已存入 sqlite，僅不再增加視覺堆疊層數。
**理由**：常見卡片堆疊 UI（如 Tinder 卡片）慣例值，避免堆太高、且不必渲染所有已建立卡片。
**時間**：2026-07-11
